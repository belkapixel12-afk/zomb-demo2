# ZOMB — Cloudflare stage33: конфигурации и подтверждение почты

Комплект подготовлен для загруженной версии `Zomb-config-codes.html`.

## Состав
- `cloudflare-worker.js` — Worker API: прежняя сигнализация WebRTC, аккаунты, друзья и приглашения сохранены; добавлены облачные сохранения, публикация/загрузка конфигураций и подтверждение почты через Resend.
- `migration-stage33.sql` — одноразовая добавочная миграция существующей D1.
- `index.html` — версия игры с интерфейсом подтверждения почты и облачными конфигурациями. Этот файл предназначен для GitHub Pages.
- `README.md` — эта инструкция.

## ВАЖНО ПЕРЕД ОБНОВЛЕНИЕМ
1. Сделай резервную копию текущего Worker и D1.
2. Используй существующие Worker `zomb-signal` и D1 `zomb-db`.
3. Не создавай новую базу, не удаляй старую D1 и не переименовывай Durable Object binding `ROOMS`/класс `Room`.
4. SQL-миграция рассчитана на старую схему из проекта (таблицы `users`, `sessions`, `friend_requests`, `friendships`, `game_invites`). Запускай её ОДИН раз. В ней есть `ALTER TABLE users ADD COLUMN email_verified...`; повторный запуск завершится ошибкой, если колонка уже существует.

## Часть 1. Подготовить почтовую отправку (Resend)
1. Создай аккаунт на Resend.
2. В Resend добавь свой домен отправителя и подтверди его DNS-записями, которые покажет Resend (обычно SPF и DKIM; следуй именно выданным записям).
3. Создай API Key в Resend. Не вставляй его в HTML, GitHub или этот архив.
4. Выбери адрес отправителя на подтверждённом домене, например `no-reply@твой-домен.ru`.

Без собственного подтверждённого домена нельзя гарантировать доставку писем игрокам на любые адреса. Не используй случайный/чужой адрес отправителя.

## Часть 2. Обновить существующую D1
В Cloudflare Dashboard:
1. Открой **Workers & Pages → D1 SQL Database → zomb-db → Console**.
2. Открой `migration-stage33.sql` из архива, скопируй весь SQL и выполни его в Console.
3. Убедись, что запрос выполнился без ошибок.

Миграция:
- добавляет `email_verified` со значением `1` для существующих аккаунтов, чтобы не заблокировать старых игроков;
- новые аккаунты создаются с `email_verified=0`;
- добавляет таблицы `player_states`, `shared_configs`, `cloud_assets`, `email_codes`.

Не запускай старый `schema.sql` поверх существующей базы вместо миграции.

## Часть 3. Подключить R2 для конфигураций с файлами
Обычные конфигурации (управление, интерфейс, лобби, профиль без загружаемых медиа) могут работать с одной D1. Для конфигураций, содержащих загруженные аудио/изображения/видео, нужен R2.

1. Cloudflare Dashboard → **R2 Object Storage** → Create bucket.
2. Назови bucket, например `zomb-assets`.
3. Открой **Workers & Pages → zomb-signal → Settings → Bindings**.
4. Add binding → **R2 bucket**.
5. Variable name: `ASSETS`; Bucket: `zomb-assets`.
6. Сохрани изменения.

Если R2 пока не подключать, публикация обычных конфигураций будет работать; загрузка медиа в облако вернёт понятную ошибку.

## Часть 4. Добавить секреты почты в Worker
Открой **Workers & Pages → zomb-signal → Settings → Variables and Secrets** (название раздела может немного отличаться).

Добавь два значения типа Secret:
- `RESEND_API_KEY` — API-ключ из Resend.
- `EMAIL_FROM` — например `ZOMB <no-reply@твой-домен.ru>` (адрес должен принадлежать подтверждённому домену в Resend).

Не добавляй API-ключ в исходный HTML, GitHub или публичные переменные. Секрет должен находиться только в настройках Worker.

## Часть 5. Обновить код Worker, не сломав WebRTC
1. Открой **Workers & Pages → zomb-signal → Edit code**.
2. Замени код Worker содержимым файла `cloudflare-worker.js`.
3. Проверь, что в настройках Worker остались прежние bindings:
   - D1: variable `DB` → существующая база `zomb-db`;
   - Durable Object: variable `ROOMS` → существующий namespace;
   - класс `Room` и его migration/compatibility настройки не удалены.
4. Deploy.

Если обновляешь через Wrangler, не используй случайный новый `wrangler.jsonc`. Нужен исходный конфиг именно твоего Worker с существующей миграцией Durable Objects и D1 binding. Сначала сохрани его копию.

## Часть 6. Проверить Worker
Открой в браузере:
- `https://zomb-signal.zomb-game.workers.dev/api/health` — должен вернуть `{"ok":true,...}`.
- `https://zomb-signal.zomb-game.workers.dev/api/v2/capabilities` — должен вернуть `version: 33`, `configs: true`, `inventory: true`, `emailVerification: true`.

Если второй адрес не отвечает или выдаёт 404, значит обновлён не тот Worker или Deploy не применился.

## Часть 7. Выложить игру на GitHub Pages как z-lore
GitHub Pages для проекта даст адрес вида `https://ТВОЙ-ЛОГИН.github.io/ИМЯ-РЕПОЗИТОРИЯ/`.

1. Войди на GitHub и нажми **New repository**.
2. Назови репозиторий, например `zomb-game` (или `z-lore`, если хочешь такой же хвост URL).
3. Для простого публичного сайта выбери Public и создай репозиторий.
4. Распакуй архив. Возьми `index.html` из комплекта.
5. Важный нюанс: HTML игры весит около 46 МБ. Веб-загрузка GitHub ограничена примерно 25 МБ на файл, поэтому загружай через **GitHub Desktop** (или Git в терминале), а не через кнопку Upload files.
6. Установи GitHub Desktop, войди в аккаунт, выбери **File → Clone repository** и клонируй созданный репозиторий на компьютер.
7. Скопируй `index.html` в корневую папку репозитория (рядом с `.git`, не в отдельную подпапку).
8. В GitHub Desktop появится `index.html` в Changes. Напиши Summary, нажми **Commit to main**, затем **Push origin**.
9. На странице репозитория открой **Settings → Pages**.
10. В Build and deployment выбери **Deploy from a branch**. Branch: `main`; Folder: `/(root)`; нажми **Save**.
11. Подожди публикацию. В Settings → Pages появится ссылка сайта.

Пример:
- логин GitHub: `whynoaq`
- имя репозитория: `z-lore`
- адрес: `https://whynoaq.github.io/z-lore/`

Чтобы получить именно такой адрес, репозиторий должен называться `z-lore` и принадлежать аккаунту `whynoaq`. Если публикуешь со своего аккаунта, адрес будет с твоим логином.

Обновление игры: замени `index.html` в локальной папке репозитория, затем в GitHub Desktop сделай Commit to main и Push origin. Не переименовывай файл в `Zomb-config-codes.html`: для Pages главная страница должна называться `index.html`.

## Часть 8. Проверка игры
1. Открой опубликованную страницу GitHub Pages по HTTPS.
2. Зарегистрируй тестовый аккаунт. После регистрации игра автоматически запросит письмо с кодом.
3. В профиле появится блок «Подтверждение почты». Введи шестизначный код из письма.
4. Выйди и войди снова — неподтверждённый аккаунт не должен проходить вход.
5. В разделе конфигураций опубликуй тестовую конфигурацию и проверь загрузку по коду в другом браузере/устройстве.
6. Проверь вход в существующий аккаунт, друзей и создание комнаты «Паутинки».

Код действует 15 минут; повторно запросить его можно не чаще одного раза в минуту. После пяти неверных попыток нужно запросить новый код.

## Что реализовано / что пока не входит
- Реализовано: подтверждение email по 6-значному коду, срок 15 минут, ограничение повторной отправки, ограничение попыток.
- Реализовано: публикация и загрузка конфигураций по коду; версия облачного состояния игрока с защитой от перезаписи более новой версии.
- Реализовано: R2-выгрузка медиафайлов, если подключён binding `ASSETS`.
- Не реализовано в этом комплекте: восстановление забытого пароля по email. Это отдельный защищённый процесс с токеном сброса и новым экраном в интерфейсе.
- Не проверено в реальном аккаунте Cloudflare: публикация Worker, DNS домена Resend, доставка писем, фактическая привязка D1/R2/DO. Это можно проверить только после настройки в твоём аккаунте.

## Важно о размере игры
Загруженный HTML содержит встроенные данные и весит примерно 46 МБ. GitHub принимает отдельные файлы меньше 100 MB, поэтому текущий `index.html` укладывается в ограничение Git. Но для удобства дальнейших обновлений и более быстрой загрузки в будущем лучше вынести тяжёлые ресурсы в отдельные файлы. В этом комплекте структуру игры специально не переписывал.
